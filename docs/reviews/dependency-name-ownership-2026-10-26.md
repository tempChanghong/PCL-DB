## 问题

同一前置出现在多个 Minecraft 版本分组时，每个按钮都会启动一次名称查询。四个分组可重复查询相同项目四次；Modrinth 前置还带版本 ID 时，原来每次又先查版本再查项目。

旧代码只在设置按钮文字时检查取消。若真实接口查询已经完成、界面线程的后续处理还排队等待，用户此时返回或重进页面，旧处理仍能写入全局名称缓存，再跳过旧按钮更新。新页面会从缓存取到已退役的名称。旧请求的清理在加入共享任务机制后，也必须避免移除同键的新请求。

## 修改

相同平台与项目的未完成名称查询由所有分组共用，只占一个并发名额。已知项目 ID 时直接读取项目名称，保留每个按钮原始的版本 ID；点击前置时继续走原有 `ResolveDependencyAsync` 及固定版本归属校验。只有版本 ID 的 Modrinth 前置仍通过版本解析项目，不能按未知项目猜测合并。

清空名称读取范围时，退役共享任务并取消原令牌。缓存写入前再次检查取消及共享任务归属；清理只移除自己拥有的任务，不影响同键新请求。失败不缓存，保留“查看前置”入口重试；不同项目仍最多并行四条查询。已完成名称缓存、平台隔离、512 项缓存上限、前置链接、版本列表和下载安装流程保留。

没有新增页面或改变布局、明暗配色、动画曲线。返回设置和重新进入详情继续使用原有页面动画；可选名称失败不能阻塞资源下载。

## 验证

新增 36 项专项：CurseForge/Modrinth × 静态浅色/动态深色 × 九项观察，使用 Mod 与数据包详情。

1. 四个分组、四个不同固定版本引用同一项目，只查询一次项目名称，四个原始版本 ID 保留。
2. 已完成名称直接复用缓存，不再联网。
3. 可选名称失败不缓存，原链接重试恢复并释放并发名额。
4. 真实 Core 查询完成后，暂扣其界面后续处理，取消再放行，旧处理不得污染新缓存。
5. 同键新查询已开始时，旧请求结束不能移除它；后续订阅者继续共用新查询。
6. 离开根页面后放行旧处理，不能写入缓存、抢回页面；返回后使用当前名称。
7. 相同数字项目 ID 在两个平台间分别缓存，前一项失败不会掩盖此独立检查。
8. 只有版本 ID 的引用保留身份：Modrinth 共用一次版本到项目解析；缺少项目 ID 的无效 CurseForge 引用保持可选失败回退。
9. 六个不同项目仍受四条并发限制；取消排队及运行中的查询后名额全部恢复，不请求资源版本列表或文件。
