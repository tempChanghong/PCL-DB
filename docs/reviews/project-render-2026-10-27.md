# 详情简介：旧图片退役后不覆盖更新的卡片

基线：`ed37d55df0ad9d6f3aa2294f4a501c529eb5409c`。沿搜索与详情的图片生命周期继续检查，发现 `RenderPackProject` 在退役旧图片请求后，不核对取消期间是否已接受更新的渲染或项目，仍会清空并替换简介行。

## PCL2 源码依据

重读固定 PCL `5ef81e490ae46b1100d61e33d0183094c7a80ca8`：

- `PageDownloadCompDetail.Init` 从当前页面参数取得项目，创建该项目的独立简介资源行，并更新来源按钮。
- `MyResourceItem` 保留资源行自己的交互、项目与图片控件；`MyImage.Source/Load` 避免相同来源重复设置，保留缓存、加载占位和本地备用图片。
- `ModLoader.State` 先改变状态，再通知令牌取消。

四份原始 Git blob 与 SHA-256 保存在 `artifacts/project-render/source/manifest.json`。本轮的渲染代次／引用检查属于桥接程序的异步交接实现，不声称上游使用相同机制。

## 复现及修复

使用真实详情图片请求的受控取消回调，覆盖两条路径：

- 旧简介图片取消时，重新渲染同项目的已验证元数据。内层已创建新简介与图片请求，外层继续替换该行并取消新请求，导致第三次图片查询及错误的可见行。
- 取消时通过实际详情入口打开另一个项目。标题、当前项目和版本失败重试已属于新项目，旧外层渲染却用原项目的简介覆盖它。迟到的新图片只更新已脱离页面的行，页面仍显示旧图标。

修复在每次简介渲染开始时记录渲染代次、原始项目和已验证项目引用；清理项目动作、退役旧图片及启动图片展示后复核归属。只有仍有效的渲染才继续创建简介和更新标题／按钮。即使是同项目的更新渲染也能使旧外层失效。

归属判定不依赖页面可见性，保留返回后的后台详情缓存；简介对象未变时仍复用原行。图片缓存、失败回退、版本列表、返回栈和动画参数不变。未改 Core、文件事务或外部启动器配置。
