# Mod 列表刷新：启动前取消通知的请求交接

基线：`995b347`。沿列表读取、目录动作、文件操作与返回继续检查，发现列表读取先取消管理／本地旧请求，之后才取得实例、分配新请求和设置加载状态，留下通知重入窗口。

## 源码依据与复现

重读固定 PCL `5ef81e490ae46b1100d61e33d0183094c7a80ca8` 的 `ModLoader`、`PageInstanceMod`、`LocalResourceLoaders`：先改变加载状态再通知取消，按当前实例实际 Mods 路径读取，同目录更新时等待。桥接程序还需处理原生配置重读、异步请求及界面归属；原始 Git blob 与 SHA-256 见 `artifacts/local-mod-read-start/source/manifest.json`。

确定性取消回调中实际调用现有入口，复现四条路径：

- 旧列表读取取消时已启动更新的刷新，旧外层调用又发起第二次查询、覆盖新请求和加载提示。
- 父管理读取取消时已启动新本地读取，旧外层刷新继续取消该请求，再执行自己的过期读取，新结果不能正常接收。
- 取消期间已返回、改选并打开另一实例，旧调用重新取得新实例并查询，把过期错误写到新页面。
- 取消期间完成更晚的读取并开始文件操作，旧刷新仍重读原生元数据，并以“正在读取”覆盖当前导入提示。

## 修复

刷新原生实例前先绑定原实例和管理／本地代次。父管理取消返回后复核原实例、目标、页面和请求状态；已有更新的操作时，旧入口直接返回，不再退役新本地请求。

本地退役流程增加一个内部登记回调：旧列表／目录／更新状态先全部退役，然后登记本次请求、代次和加载门控，最后才通知旧令牌。更晚的强制刷新或导航可以再次退役本次请求，旧入口在原生读取前复核归属并退出。异常反馈及最终清理同时检查代次和请求身份。

内部回调为可选参数，原导航和文件操作的默认取消路径保持。原生配置、隔离／共享目录解析、文件事务、读写等待以及动画时序未修改。
